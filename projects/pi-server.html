Pi Server

I wanted one page that could tell me whether anything at home was broken. It turned into a full monitoring and control stack running on a Raspberry Pi 5.

What it is

A single-page control panel for my home network. It runs as a system service on a Raspberry Pi 5 and shows live hardware stats for the Pi and my desktop, an inventory of everything on the network, the status of the services I self-host, and controls for the things I'd otherwise have to walk across the house to do.

The brief I gave myself was narrow: everything I want to know should be visible without clicking, and everything I want to do should be one button. Every feature since has had to earn its place against that.

What it does

  • Live system stats. CPU, memory, temperature, disk and uptime for the Pi, streamed over a WebSocket rather than polled, so the numbers move in real time instead of stepping.
  • Desktop monitoring. A companion agent runs on my Windows PC and reports CPU, memory, disk and GPU telemetry back to the dashboard. GPU stats come from NVIDIA's management library directly.
  • Remote power control. Wake-on-LAN to start the PC, and a queued command channel for sleep and shutdown, so a control issued while the PC is off isn't lost — it's picked up when the agent next checks in.
  • Network scanning and device inventory. Regular scans discover what's connected; results are stored in SQLite with history. Devices can be searched, sorted, tagged by type, renamed, annotated, marked as reviewed, or deleted — so an unknown device is a one-time question, not a recurring one.
  • Ad blocking. Integrates with the Pi-hole API rather than reimplementing it, surfacing query and blocking stats alongside everything else.
  • Connectivity. Latency polling, on-demand speed tests, and a VPN status panel with a restart control for when the mesh network gets stuck.
  • Alerts. Threshold and service-health alerts delivered as push notifications to my phone, so I find out something's wrong without having the dashboard open.

How it's built

Backend

Python and FastAPI. Stats that change constantly go out over WebSockets; everything else is a plain REST endpoint. Device history and scan results live in SQLite. Network discovery shells out to nmap and parses the results. External integrations — the ad blocker's REST API, the VPN's status output, the push notification service — are each wrapped behind a small module so a change on their side touches one file.

Frontend

Hand-written HTML, CSS and JavaScript with no framework. The layout is a four-region shell: a permanent left navigation sidebar moving from the overview down through each subsystem, a top bar with labelled status dots for at-a-glance health, a card grid as the main content area, and a right sidebar on the overview page holding a merged Pi-and-PC stats card. Adding a page means adding a nav entry and a content module, nothing else.

Deployment

The dashboard runs as a systemd service, so it starts on boot and restarts itself if it crashes. The PC agent starts automatically through Windows Task Scheduler under a dedicated local account.

Problems worth solving

  1. Config that survives its own updates

    Early on, updating the dashboard meant replacing the application directory — which also wiped the credentials and settings stored inside it. Now every piece of persistent state lives in a separate config directory outside the application tree: service credentials, the target machine's identifiers, the notification topic, and the device database. Updating is now a directory swap with nothing to back up first.

  2. Commands for a machine that isn't listening

    Sleep and shutdown can't be pushed to a PC that's asleep, and Wake-on-LAN is fire-and-forget with no acknowledgement. Instead of trying to make the dashboard talk to the PC synchronously, controls write to a command queue that the agent drains on its own schedule. The dashboard's job is to record intent; delivery is the agent's problem.

  3. An ISP gateway that won't cooperate

    Running ad blocking network-wide requires pointing DHCP at the Pi for DNS, and the supplied gateway locks most DHCP settings and exposes no DNS field at all. Rather than fight it, I mapped the two real options — per-device DNS overrides, which I've proven out, or bridge mode with my own router — and documented the trade-off. Sometimes the correct engineering answer is that the constraint is external and the fix is hardware.

  4. A second path to the PC

    Wake-on-LAN over Wi-Fi is unreliable by design. I added a direct Ethernet link between the Pi and the desktop as a dedicated control path, configured as its own network profile so it coexists with the normal Wi-Fi connection instead of competing with it.

Where it's going

  • Historical graphs built from periodic SQLite samples, so I can see trends instead of only the current moment.
  • Per-device bandwidth and a scheduled speed-test history.
  • Deeper ad-blocker reporting — top blocked domains and top clients.
  • Container health cards and a searchable alerts log.
  • Personal cloud storage as the next major addition, planned as a containerised stack on external storage. Treating it as a proof of concept first, since the storage I have on hand isn't rated for that write load.
