Snake Gone Rogue

Snake is a solved problem. So I broke it: added a shop, permanent upgrades, run modifiers and a debt you have to pay off, then spent most of my time on the rendering.

What it is

A roguelite where the run loop is Snake. You eat apples to earn currency, spend it in a shop between rounds, and try to hit a quota that climbs every round. Miss it and the run ends — the debt system means playing it safe eventually loses too, so you're pushed into taking risks you don't want to take.

Upgrades come in two flavours. Temporary ones last the current run and stack in ways I deliberately didn't balance too carefully, because the broken combinations are the fun part. Permanent ones are bought with a separate currency and persist across every future run through a slot-based save system, so the game opens up the longer you play it.

What's in it

  • A shop with real decisions. Scrollable temporary upgrades, a randomised set of permanent slots with per-slot purchase locks, a reroll, and a modifier reveal that shows what you're signing up for before you commit.
  • Run modifiers. Conditions rolled at the start of a run that change the rules — board size, speed, apple behaviour — and shift the risk calculation for everything you buy.
  • Multiple apple types. Standard, rotten, silver and frost, each with different effects on score, length and speed.
  • Endless mode. The board wraps on both axes, so the play space is topologically a torus. This turned out to be the hardest part of the whole project.
  • Checkpoints and pausing. Between-run continuity so a long session doesn't have to be one sitting.
  • Persistent saves. Multiple slots, each holding permanent upgrades, currency and progression state.
  • Custom assets. Hand-drawn 16×16 sprites for every snake segment orientation and apple variant, a seamless pattern texture for the body, a pixel font, and sound effects loaded through a central manager.

How it's built

The codebase is split into four packages that each own one concern: game/ for rules and state, screen/ for everything drawable, system/ for shared services, and data/ for saves and definitions. Screens are self-contained modules rather than branches in one giant loop, which is what made it possible to add a shop, a pause screen and a checkpoint flow without the main loop turning into a maze.

Sprites, sounds and fonts load once at startup through a SpriteManager, a SoundManager and app-level dictionaries, so nothing touches the disk mid-frame. The pixel font is wrapped in a small class that handles automatic uppercasing and blends in fallback glyphs when a character is missing from the typeface, which saved me from drawing an entire character set by hand.

Movement is interpolated per frame rather than snapping cell to cell. The snake logically moves on a grid, but visually it slides, which means every rendering problem below is really a problem about the gap between those two representations.

Problems worth solving

  1. Rendering a wrapping snake without flicker

    In endless mode the board wraps, so a snake crossing the right edge has to appear on the left at the same time. My first approach decided, for each point in the body, which copy of the board it was nearest to. That works right up until two adjacent points disagree, at which point a segment stretches across the entire screen for one frame and the whole thing strobes.

    The fix was to stop thinking per point. The final renderer draws the entire body as rigid complete copies, each offset by a whole board width or height. Every copy is internally consistent because it's the same geometry translated; the ones off screen are simply never seen. Flicker gone, and the code got shorter.

  2. Apples that move across a wrapping board

    Moving apples needed two separate fixes that I initially thought were one bug. The first was logical: their position had to loop at the wrap boundary rather than run off the edge. The second was visual: an apple near a corner can legitimately need to appear in more than one place at once, which meant checking a three-by-three neighbourhood of board tiles and drawing a copy wherever it landed on screen.

  3. Input that doesn't eat your turns

    At speed, players queue two direction changes faster than one game tick. Handling input directly meant the second press overwrote the first and the snake missed the turn — or worse, accepted a reversal into its own neck. Direction changes now go into a queue that's drained one per tick, with each entry validated against the direction actually in effect when it's consumed rather than when it was pressed.

  4. A body that overlaps itself while interpolating

    Smooth movement means segments occupy fractional positions between cells, and during a turn the drawn quads for two neighbouring segments can overlap and produce a visible seam or a doubled outline. Getting this right took rewriting the ribbon renderer twice, and the final version draws the body as a continuous textured strip rather than a sequence of independent sprites.

Where it's going

The engine and the systems are in good shape; what holds the version number back is content breadth. The plan is more modifiers, more upgrades and more apple types, plus another balance pass on shop pricing now that the permanent upgrade pool is larger.

Background music is the other open item. It needs its own scheduler instance so stopping the music doesn't also kill sound effects, which is exactly the sort of thing I'd rather design once than patch around later.
