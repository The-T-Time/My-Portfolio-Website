RainCheck

Every weather app tells you what one provider thinks. RainCheck asks several, notices when one of them is wrong, and tells you what the rest agree on.

What it is

A native Android weather app, written in Kotlin against the classic View system rather than Compose. Current conditions, an hourly and daily forecast, severe weather alerts, and a notification system I actually leave switched on.

The thing that makes it different is underneath. Forecast providers disagree, sometimes badly, and picking one means inheriting whatever that provider gets wrong in your area. RainCheck queries several and combines them, which turns a data-source problem into a statistics problem.

The part I care about most

Combining sources that disagree

Averaging several forecasts sounds like it should be a one-liner, and it isn't. A plain mean is exactly as vulnerable to one bad source as using that source alone would be — a provider reporting a temperature twenty degrees off drags the average with it, and the user has no way to know.

So before anything is averaged, outliers are rejected. The app uses a modified Z-score based on median absolute deviation, which is a robust measure: unlike standard deviation, it isn't itself distorted by the outlier it's meant to catch. Values that fall too far from the median get dropped, and only the surviving sources are averaged.

The result is a forecast that degrades gracefully. One provider going down or going haywire doesn't show the user a wrong number; it just slightly widens the spread of what's left.

What's in it

  • Three independent notification types. A daily summary on an exact alarm, precipitation warnings on background work scheduling, and severe weather alerts from the national service. They're genuinely separate systems because they have genuinely different timing requirements — a daily briefing must arrive at a specific minute; a precipitation check can be batched.
  • Shared notification plumbing. All three build their content through one builder and check one event tracker for deduplication, so you don't get told about the same storm twice by two different systems.
  • Precipitation classified properly. Rain, drizzle, thunderstorms, snow, and freezing rain or sleet are distinguished and each gets its own notification wording. "Precipitation expected" is not useful when the answer is black ice.
  • A real permission model. Location permission is treated as three states — always, while in use, and denied — instead of the usual granted/not-granted binary, because background notifications need something foreground display doesn't.
  • Theme switching with an animated transition, and slide transitions between screens applied at theme level so navigation is consistent everywhere.

Problems worth solving

  1. Disabled controls that explain themselves

    If you haven't granted background location, the controls depending on it should be visibly unavailable — but a control that's fully disabled can't tell you why it's unavailable, which leaves users stuck. The solution was to separate the two concerns that "disabled" normally bundles together: transparency handles the visual dimming so the control reads as inactive, while the touch handler stays live and shows an explanation with a route to fixing it.

  2. An expand animation without the flash

    Expanding a forecast row with Android's default automatic transition produced a visible flash, because the default runs its fade and its bounds change in sequence — briefly showing content at the wrong size. Composing the transition by hand, with the bounds change and the fade running in parallel, removed it. It's the kind of fix nobody notices, which is the point.

  3. A master switch that doesn't destroy your settings

    Turning notifications off globally and back on used to reset every sub-setting to its default, silently undoing configuration the user had done deliberately. The master toggle now gates delivery without writing to the individual settings at all, so flipping it twice returns you exactly where you were.

  4. Deleting code as a feature

    Before publishing I did a full cleanup pass: removed dead utility classes, unused API endpoints, stale manifest entries, invalid resource qualifiers, orphaned strings, and around 130 unused drawable icons. I also renamed internals that had drifted from what they actually meant — a field called rainChance that had long since covered all precipitation became precipChance. A codebase that lies about itself is a codebase you can't trust six months later.

Published properly

The repository ships with a README, an architecture document, an API reference and a changelog, plus an MIT license. All traffic is HTTPS; the cleartext exemption was removed rather than left in place "just in case". API keys are kept in a local properties file that's excluded from version control, so there was never a secret to redact.
